# Векторные шрифты SPML (`sfon`)

Ресурсы шрифтов (тип 4 в `mmi_res`, модуль 1) — это файлы `sfon` движка **SPML** (Spreadtrum),
по одному на письменность. По сути это урезанный TrueType/OpenType: стандартные `cmap`, `GDEF`, `GSUB`, `GPOS`
плюс собственная упаковка глифов. Все числа big-endian.

Проверено на всех 7 шрифтах 3210 11.00 HK: **38 853 глифа** разбираются, и каждый занимает свои байты
ровно до конца. Таблицы идут вплотную, без промежутков.

Инструмент: `python3 -I tools/sfon.py <file.sfon>`; в Python — `Sfon(bytes)`, `.outline(gid)`, `render_text(...)`.

## Откуда известно

USER_IMG 11.00 HK (база `0x88000000`), модули SPML:

| Адрес | Файл | Что делает |
|---|---|---|
| `0x88079ac0` | spml_font.c | загрузка `sfon`: заголовок, таблицы, наборы (strikes) |
| `0x880791b0` | spml_font.c | поиск глифа по номеру в наборе |
| `0x880794a2` | spml_font.c | выбор набора по размеру, масштаб `size × ppem / 128` |
| `0x8807957a` | spml_font.c | метрики глифа (флаги, advance) |
| `0x884ed954` | spml_image.c | контур: составной (TrueType-composite) или простой |
| `0x884ed168` | spml_image.c | распаковка простого контура (типы 3 и 4) |

Остальные модули SPML: `spml_otf_cmap.c`, `spml_otf_gsub.c`, `spml_otf_gpos.c`, `spml_otf_kern.c`,
`spml_autofit.c`/`spml_afhints.c` (порт автохинтера FreeType), `spml_bidi.c`, `spml_resolve_*.c` (шейпинг для
арабского, индийских, тайского, кхмерского, мьянманского, тибетского письма).

## Файл

| Смещение | Что |
|---|---|
| 0x00 | `sfon` (`SPRD_FONT_TAG`) |
| 0x04 | u32 `sprd_version` = 1 |
| 0x08 | тег письменности: `latn`, `cyrl`, `han`, `hani`, `arab`, `hebr`, `beng` |
| 0x0c | u16 `version` = 3 |
| 0x0e | u16 число наборов (strikes); во всех шрифтах 3210 = 1 |
| 0x10 | u16 = 1 (назначение не выяснено) |
| 0x12 | u16 units per em (1000 или 2048) |
| 0x14 | u32 смещения таблиц: `cmap`, `GDEF`, `GSUB`, `GPOS`, `kern` (0 = нет) |
| 0x28 | u32 смещение набора × число наборов |

Таблицы `cmap` (формат 4, platform 3/encoding 1), `GDEF`, `GSUB`, `GPOS` — стандартные OpenType.
У арабского, иврита и бенгали есть GDEF/GSUB/GPOS (скрипты `arab`, `latn`, язык `FAR`…); у латиницы, кириллицы и китайского — только `cmap`.

## Набор (strike)

Заголовок 0x22 байта:

| Смещение | Что |
|---|---|
| 0x00 | u8 размер набора (108 для `latn`, 115 `cyrl`, 125 `han`) |
| 0x10 | u8 advance по умолчанию |
| 0x11, 0x12, 0x13, 0x14 | значения по умолчанию для растровых наборов (lsb и др.) |
| 0x15, 0x16 | u8 масштабируемые метрики строки (используются как высота/базовая линия) |
| 0x17 | u8 тип: 3, 4 — векторный; иначе растровый |
| 0x18 | u8 флаг (проверяется при кешировании) |
| 0x1a | u16 число глифов |
| 0x20 | u16 число сегментов `S` |

Затем `u16 end[S]`, `u16 start[S]`, `u16 first[S]`, `u32 off[число глифов]`.
Глиф `g` из сегмента `k`: индекс `first[k] + g − start[k]`; данные по адресу `набор + off[i] + 0x20`,
длина до следующего смещения. Номера глифов идут с пропусками.

## Глиф

Байт флагов:
- `0x01` — составной глиф;
- `0x08` — следом u8 advance (в 1/32 размера набора), иначе берётся advance по умолчанию;
- для растровых наборов ещё `0x10`, `0x20`, `0x40`, `0x80`, `0x04` — дополнительные метрики.

**Составной** — как в TrueType: u16 число компонентов, для каждого u16 флаги, u16 глиф, смещения (s16, если флаг `0x01`, иначе s8),
масштаб F2Dot14 (`0x08` — один, `0x40` — по X и Y, `0x80` — матрица 2×2).

**Простой (тип 3)**:
- u8 `h`: `h&1` — число точек u8 (иначе u16), `h&2` — число контуров u8 (иначе u16), `h&4` — концы контуров u8 (иначе u16);
- флаги точек как в TrueType, с повтором (`0x08` + счётчик);
- X: `0x02` — u8 со знаком из `0x10`; иначе при `0x10` X не меняется, иначе s16. Y так же с `0x04`/`0x20`;
- концы контуров идут **в конце**, а не в начале, как в TrueType;
- `0x01` — точка на кривой; `0x40` — **кубическая** контрольная точка, иначе квадратичная.

Тип 4 (в 3210 не встречается) упакован побитово: X и Y дельты по 8 штук с битовыми масками «как у предыдущей».

## Запись (tools/sfonwrite.py, tools/ttf.py, tools/ttf2sfon.py)

Правила стокового энкодера восстановлены так, что **все 38 853 глифа** всех шрифтов (включая китайские с кубическими
кривыми) кодируются заново байт в байт, а файлы шрифтов и наборы собираются из своих частей байт в байт:
- байт флагов глифа: `0x02` у всех глифов (смысл не выяснен), `0x01` — составной, `0x08` — advance отличается от
  значения по умолчанию в заголовке набора (тогда следом u8 advance);
- точки: дельта 0 пишется **не** флагом «то же значение», а коротким `+0` (`0x02|0x10` / `0x04|0x20`); |дельта| ≤ 255 —
  коротко со знаком во флаге, иначе s16; одинаковые флаги подряд — всегда повтор `0x08` + счётчик (уже с двух);
- байт `h`: `1` — точек < 256, `2` — контуров < 256, `4` — последний конец контура < 256 (у пустого глифа бит 4 не ставится);
- набор: заголовок 0x22 (`+0x00` и `+0x18` — «размер набора», `+0x10` — advance по умолчанию, `+0x15/+0x16` — метрики строки,
  `+0x17` — тип 3, `+0x1a` — число глифов, `+0x1c` — u32 `0x20`, `+0x20` — число сегментов), сегменты подряд идущих номеров
  глифов, смещения от `набор + 0x20`, глифы подряд в порядке номеров;
- файл: заголовок 0x2c, затем `cmap`, `GDEF`, `GSUB`, `GPOS`, набор — без выравнивания.

`cmap` пишется своя (одна подтаблица формата 4, сегмент на серию подряд идущих символов, добивка до 4 байт): по формату
это то же, что у стока, но байт в байт не совпадает (их инструмент склеивает серии через промежутки); сопоставление
символ → глиф восстанавливается нашим читателем у всех 7 шрифтов без потерь.

**Единицы.** Advance — u8 в 1/32 em (проверено: «H» 23 → 719, «i» 8 → 250). «Размер набора» (108 латиница, 115 кириллица,
125 китайский) — масштаб `size/128` к кеглю (по коду загрузчика), поэтому кириллица в стоке рисуется на ~6% крупнее
латиницы (**оценка** по коду, на телефоне не проверено).

**TTF → sfon** (`ttf2sfon.py`): набор символов и номера глифов остаются заводскими; символ, который есть в TTF, получает
контур из TTF; остальные остаются заводскими (составной глиф из одних заводских деталей копируется как есть, иначе
разворачивается в простой заводской контур). Контуры масштабируются так, чтобы видимая высота строчных
(`высота «x» × размер набора / 128`) совпала с заводской латиницей — латиница и кириллица получаются одного роста.
Поддерживаются TrueType-контуры (`glyf`, в т. ч. `.ttc`), CFF — нет.

```bash
python3 -I tools/ttf2sfon.py <mmi_res> <новый> /System/Library/Fonts/Supplemental/PTSans.ttc:0
```

Проба на PT Sans (лицензия OFL — можно ставить в свою прошивку): латиница 332 символа из PT Sans, 1028 редких остались
заводскими; кириллица 207 из PT Sans, 59 редких (старославянские и т. п.) заводские. Размер: латиница 87 → 152 КБ,
кириллица 23 → 31 КБ (контуры PT Sans сложнее, а составные редкие буквы развёрнуты). Изменились только эти два шрифта,
все глифы читаются. Сравнение рендером — `work/mod_test/font_compare.png`.

## Наблюдения

- `han` (7.2 МБ, 21 465 глифов) и `hani` (4.7 МБ) — китайский; это 12 из 18.6 МБ ресурсов сборки HK.
- Кириллица — отдельный маленький шрифт на 311 глифов (23 КБ); латиница — 1 420 глифов.
- По начертанию гарнитура похожа на Noto Sans / Open Sans.
