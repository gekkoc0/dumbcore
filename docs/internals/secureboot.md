# Подпись образов и Secure Boot (UMS9117)

Разобрано из DHTB-образов наших 8 прошивок (`tools/dhtb.py`), кода BOOT0/BOOT1 (Ghidra/armre)
и `fwcrypto.c` из fphelper_t117 (public domain).

## Формат подписи DHTB

Каждый образ FDL1, FDL2, BOOT0, BOOT1, KERNEL, USER = заголовок DHTB (0x200) + полезные данные + **подпись**.

| Поле | Что |
|---|---|
| DHTB +0x00 | `DHTB`, u32 версия=1, +0x30 u32 размер данных; данные с 0x200 |
| sign_head (0x60) | смещение и размер блока подписи |
| sign_data | u32 тип (0/1), u32 бит ключа (**2048**), e (4 байта), n (256 байт), SHA-256 данных, SHA-256 ключа, anti-rollback версия, **RSA-подпись PKCS#1 v1.5** |

**Все 48 образов (6 файлов × 8 сборок) проверяются полностью:** и хэш данных, и RSA-подпись сходятся. ✔ (`tools/dhtb.py`)

**Три ключа** (одинаковы во всех сборках, включая 14.03 и 15.00):

| Ключ (SHA-256, первые байты) | Чем подписано |
|---|---|
| `684648…` | FDL1, BOOT0 |
| `f0bfca…` | FDL2, BOOT1 |
| `a76802…` | KERNEL, USER |

Все моды (`MOD_nogame…`) подписаны **теми же** ключами HMD — значит, их собрали из файлов, которые уже
подписаны, и подпись не пересчитывали. Менять можно только то, что лежит **внутри** подписанного образа
без изменения его длины? Нет — хэш считается по всем данным, так что любое изменение ломает подпись.
Почему же моды работают — см. ниже.

## Цепочка проверки (из кода)

BootROM → FDL1 → FDL2, и при прошивке BOOT0 → BOOT1 → KERNEL. У каждого звена свои строки:
- FDL1: `start verify fdl2`, `verify fdl2 suc/fail`;
- BOOT0: `start verify boot1`, + строки сертификатов: `cert type invalid`, `key cert hash verify fail`,
  `content cert hash verify fail`, `antiroll_back error`, `compare hash fail`, `cert empty`;
- BOOT1: `start verify kernel`, `verify kernel suc/fail` (функция `0x80100542`, проверка `0x80102212`).

## Ключ к загадке: eFuse

Проверка подписи **условная**. В BOOT1 функция `0x8010201e` перед проверкой читает конфиг из **eFuse**
(`0x80100e50`: база eFuse `0x40240000`, слова с `0x40241000`; та же `EFUSE_BASE`, что в fphelper) и тестирует
бит: если бит Secure Boot в eFuse **прошит** — образ проверяется и при несовпадении не грузится; если **не прошит** —
путь проверки пропускается.

**Отсюда объяснение второй ревизии и ошибки `UB1132` (гипотеза, не проверена на железе):**
- Стоковые прошивки HMD всегда подписаны настоящим ключом — поэтому на любом телефоне они ставятся.
- Телефон **enforced** Secure Boot (eFuse прошит) отвергнет чужой/изменённый FDL или образ → ошибка записи.
- Подтип **SV:19@2025**, который на 4PDA смогли прошить старыми FDL, скорее всего, имеет eFuse Secure Boot
  **не прошитым**, поэтому принимает неподписанные/старые FDL. SV:20/21@2026 — вероятно, прошитый.

Проверить это можно только на самом телефоне: прочитать eFuse через кастомный FDL (`t117_fdl`) командой
`read_mem`, но кастомный FDL сам неподписан, и на enforced-устройстве он не загрузится — то есть сам факт
«не грузится» и будет ответом.

## Почему моды с форума работают — подтверждено хэшами

Сверка разделов мод-сборки `MOD_nogame4F2` со стоком 11.00 (md5 из `tools/extract_all.py`):

| Раздел | Сток 11.00 | MOD_nogame4F2 | |
|---|---|---|---|
| USER_IMG (подписан) | `470c5c27` | `470c5c27` | **совпадает** |
| KERNEL_IMG (подписан) | `4b90023f` | `4b90023f` | **совпадает** |
| MMIRes (ресурсы) | `0dba9c60` | `4f2cca52` | изменён |
| NV (nvitem) | `f411a992` | `66e1b0f9` | изменён |

➡ **Разгадка:** моды **не трогают подписанные образы кода вообще.** Они меняют только `MMIRes` и `NV` — а это
**отдельные разделы `.pac`, не входящие в подписанные DHTB-образы.** Поэтому подпись кода остаётся валидной,
и моды ставятся даже там, где Secure Boot включён. Все 48 code-образов в прогоне `dhtb.py` дали `HS`, потому что
code-часть у модов стоковая.

Вывод для нас: **ресурсы (иконки, картинки, шрифты), тексты и NV (меню, настройки) лежат вне подписи и меняются
свободно; код (KERNEL/USER) под подписью.**

## Вывод для целей проекта

- **Иконки, шрифты, тексты, цвета, меню (NV)** — отдельные разделы, подписью кода не защищены → менять можно
  даже при включённом Secure Boot (нужно только уметь собрать `.pac`).
- **Патч кода** (например, ради GIF-обоев, если их нет в NV-настройке) защищён подписью KERNEL/USER. На устройстве
  с прошитым eFuse он не загрузится; приватного ключа HMD нет. На устройстве без прошитого eFuse — загрузится.
- Твой телефон: сначала выяснить состояние eFuse (косвенно — принимает ли он кастомный FDL). До этого код не патчить.

## Проверено на телефоне с ПО 16.00 (15.11.2026, docs/backup.md)

Загрузчик ПЗУ на ответ «check baud» вернул версию `SPRD3` — так отвечают аппараты **без** включённой защищённой
загрузки (`spd_dump` выставляет флаг secure boot, если ответ другой). Родные FDL1/FDL2 из `.pac` приняты и запущены.
Подписи RSA образов boot0/boot1/kernel/user на телефоне сходятся (`tools/dhtb.py`). Что именно проверяет загрузчик
при старте (подпись kernel/user против ключа в eFuse) — по-прежнему вопрос: проверять осторожно и только после бэкапа.
